# 差旅助手 2.0 离线自动化测试方案

状态：已实现部分离线测试，实际范围与运行方法见 `offline/README.md`；本方案全矩阵尚未完成验收。日期：2026-11-04。

## 1. 目标与边界

本次只验证项目代码的确定性行为：输入输出契约、前置门控、调度依赖、缓存复用、约束求解、结果校验、记忆隔离、幂等及异常处理。

全套测试不得调用真实 LLM、联网搜索、天气接口、模型下载、Hugging Face、正式 PostgreSQL/Redis/Milvus 或正在运行的 pi-durable；不得使用真实 API Key，也不启动正式服务。测试依赖须提前安装；依赖缺失时明确失败或标记不可运行，不在测试中自动安装或下载。

模型替身只按预先指定的顺序返回固定输出，并记录调用次数及输入。测试通过表示代码正确处理了这些输出，不表示真实模型能够理解需求、提取约束或生成合格行程。不得据此发布 ChinaTravel 官方成绩、真实规划通过率、真实服务恢复保证或端到端性能提升结论。

## 2. 当前项目需要先处理的问题

- `tests/eval/run_eval.py` 混合真实模型评测和单元测试，有两个 `__main__` 入口；直接运行会先进入真实模型评测，不能作为本次安全入口。
- 部分现有测试直接构造 ExecutionTracer，可能连接本机 PG；部分恢复测试在 PG 不可用时跳过。不能原样纳入“全隔离”测试并宣称通过。
- MemoryManager 默认读取正式配置，并可能降级写 `data/memory`；必须显式传 `postgres_config=False`、`redis_config=False`、临时 storage_path，不能只靠服务未启动实现隔离。
- 用户 pipeline、会话绑定、调度缓存和追踪上下文存在共享可变状态，需要重点测试同一用户不同会话的交错执行。
- 新导入 ChinaTravel 有 1604 条需求，但尚无当前项目的约束评分适配器；原始 DSL 不能直接当本项目的可执行测试。

本次另建 `tests/offline/`。原始在线评测入口保持独立，不在默认测试发现范围内。已有测试逐项审查、迁移后复用，避免同时进行大规模重构。

## 3. 隔离设计：隔离失败必须可见

### 网络与模型

使用 pytest 的自动 fixture，在导入业务模块之前拦截真实 socket 连接、HTTP 发送及数据库连接入口。HTTP 模拟使用内存 transport；FastAPI 使用 TestClient 的进程内 ASGI 通道，不监听端口。模型工厂改为可注入 ScriptedModel；任何未替换的真实模型调用均抛出 TestIsolationViolation。

仅设置假密钥或关闭 pi-durable 开关不够，因为 SDK、检索和存储仍可能发请求。测试进程不继承真实凭据；只在独立进程的环境中覆盖测试值，不编辑 `config.py`，不输出配置对象或密钥。

业务代码可能捕获网络错误并自动降级，因此禁止访问时还要记入独立的违规记录器；每条测试 teardown 检查违规数为零，防止异常被业务吞掉后测试假通过。刻意测试“连接失败降级”时，使用注入的故障连接器，不真的尝试连接。

### 文件与存储

- ChinaTravel 原始文件和现有 `cases.json` 只读；测试前后检查 SHA256。测试加载中文 query，不向模型替身上下文注入验收用实体或原生 DSL。
- 所有记忆、临时知识库、SQLite checkpoint、报告均写入本次创建的临时根目录。文件写入守卫对根目录外的创建、写入、重命名和删除进行拒绝与违规记录；关闭业务日志落盘，禁止生成 `.pyc`，pytest 缓存也指向临时目录。
- 内存/JSON 存储用于验证实际降级逻辑；FakeRedis/FakePG 只用于协议和分支测试，不声称覆盖真实 Redis/PG 的并发、事务或持久性。
- 不打开或复制 `data/pi-durable/session.sqlite`，不读取真实用户记忆。不运行 SQL 清表、FLUSHDB 等清理操作。
- 通过 pytest 临时目录生命周期清理资源；Windows 上先关闭文件、数据库连接和子进程，再删除。失败诊断仅保留本次测试的临时产物。

### 用户、会话和进程

每个测试使用独立 user_id、session_id、request_id、turn_id，包含 run_id 与 case_id。对照测试刻意使用“同用户不同会话”“不同用户同会话名”“相同 request_id 不同用户”等组合，验证真实的隔离边界；不能因为所有 ID 都不同就认为已测隔离。

每个测试重建 AppState、pipeline、熔断器、幂等守卫及追踪缓冲。缓存和模块单例由 fixture 保存并恢复；清理不能只执行 clear，否则会误删进入测试前的状态。时间、随机种子和异步执行顺序受控。

## 4. ChinaTravel 在本次测试中的角色

对全量 1604 条执行数据资产校验：四个划分条数、ID 唯一性、CSV 与 JSON 中文原文及约束一致性、字段类型、非空需求、来源版本及 SHA256。校验失败退出非零。

不通过关键词从自然语言“猜出”日期、预算或必去项后充当标准答案，不执行 `hard_logic_py`。它是上游 DSL 文本，并非已适配的本地验收程序。

代码场景使用人工复核的少量派生 fixture，分别保存：

1. 原始 query 和 source_uid；
2. 固定的模型输出（意图、实体、技能生成文本）；
3. 独立编写的预期状态、调度次数及结果断言；
4. 修改说明，例如“增加固定日期”“将某活动设置为必去”。

只选 Easy/Medium/Human 中约 12～20 条作为可读的代码场景素材；Human1000 除完整性校验外保留为后续独立模型评测集。日期统一固定测试时钟，不修改上游原题。派生案例不计为新增官方需求。

这些测试是“给定意图输出后代码如何执行”，不是“系统理解了 ChinaTravel 的需求”。不以固定模型替身跑完 1604 条来制造规划通过率。

## 5. 测试矩阵与验收点

| 模块 | 关键输入/场景 | 必须断言的代码行为 |
| --- | --- | --- |
| 契约归一化 | 字符串 null、非法枚举、缺字段、嵌套偏好、数字金额 | 合法输出结构、约定默认值、输入未意外修改；不把任意非法金额静默视为零 |
| 前置门控 | 缺目的地/天数/日期；字段齐全；end_date 可推导 | 缺失集合正确、状态 needs_input；被门控技能调用次数为零；输入齐全才执行 |
| 技能元数据 | 别名、consumes、safe/unsafe 声明 | 调度名映射一致、仅传允许的前序数据、未声明或非法声明采用明确策略 |
| 分层调度 | 同层独立技能、后层依赖、一个技能失败 | 使用 asyncio Event/屏障证明同层并发；P2 必须等 P1 settled；失败范围及聚合状态正确 |
| 快速路径 | 单技能无依赖；声明依赖但前序未满足 | 仅符合条件时启用，调用一次；与普通路径的公共输出契约一致 |
| 局部重规划 | 仅改偏好；改城市/日期/人数/天数；上轮失败 | 仅复用仍有效的结果；影响对应信息源的变化必须使缓存失效；失败结果不复用 |
| 求解器 | 小型手工活动池、时间窗、交通间隔、必去项、恰好预算、超预算、无解 | 独立重算每项硬约束；无解明确返回，不静默删必去项；不要求唯一排程顺序 |
| 行程校验器 | 合法计划，单独破坏天数/必去项/花费/时间间隔 | 坏例被对应规则捕获，合规边界放行；明确活动预算与全行程预算的区别 |
| 费用/冲突校验 | 合计错误、上下限、区间接触/重叠、过去与未来行程 | 依据当前业务口径进行正反例断言；暂未检查的规则单列缺口，不能声称已覆盖 |
| 有界修复 | 第一次坏、第二次好；连续坏；解析异常 | 调用次数符合上限；第二次输入携带具体缺陷；最终失败/警告与实际结果一致 |
| 幂等 | 并发同请求、完成回放、失败重试、TTL、跨用户同键 | 一次业务执行、响应一致；失败后可重试；不同租户互不命中 |
| 记忆/缓存 | 偏好追加覆盖、写后失效、滑动窗口、TTL、JSON 往返 | 验证真实内存/JSON实现；不同用户隔离、同用户按约定共享长期偏好且隔离短期会话 |
| 会话交错 | A 请求暂停→B 切会话执行→A 恢复 | A 的记忆、响应 session_id、trace、缓存不能写入 B；通过调度屏障稳定复现竞态 |
| API 契约 | /chat、内部技能端点、异常、错误令牌 | 通过进程内接口验证状态码、响应字段和隔离；后台总结不得调用真实模型 |
| 运行状态 | 成功、敏感路由、意图异常、编排异常、取消 | in-flight 回到零、幂等键按约定释放、资源关闭；隔离违规不可吞掉 |
| Durable 客户端 | 固定 prepare/generate/parse 回应、超时、不可用 | 使用假 transport 验证协议、重试边界、上下文传递，不声称已测真实崩溃恢复 |

重规划矩阵中“换城市后缓存失效”等是正确性目标，不预设当前代码已实现。测试暴露问题时先报告失败和最小复现，不降低断言以匹配现状；业务修复另行实施。

## 6. 求解器与持久任务的验证方式

求解器测试使用真实 OR-Tools 和最多 3～6 个活动的手工数据，不调用 LLM。采用手工可验证的可行/不可行样本；小规模时可用独立穷举 oracle 对照可行性或最优分值，不复制生产实现来计算答案。固定参数和计算预算；不以墙钟耗时判断并发，也不把求解超时等同于数学无解。

pi-durable 分两档：

- 默认离线档：测试真实任务定义与模拟 runtime/HTTP 的状态迁移，只证明协议与代码分支。
- 独立可选离线档：仅在安装所需 Node 依赖且能注入内存 provider 时，使用临时 SQLite 运行真实 durable runtime；重启测试在独立子进程中进行。先落 checkpoint、记录派发，再终止并重建进程。safe 按预期重放，unsafe 按策略跳过；任何副作用计数保存在该测试临时目录。不能用简单重建 Python 对象替代真实进程恢复测试。

若运行库无法在无网络环境使用，本次明确列为未验证，不启动正式服务补测。测试替身的持久化不能证明真实库的持久化能力。

## 7. 测试组织与运行入口（拟新增）

```text
tests/offline/
  pytest.ini
  conftest.py                 # 自动隔离、受控时钟、状态复原
  fakes.py                    # 固定模型输出、存储及传输替身
  fixtures/                   # 人工审核输入与独立预期，记录 source_uid
  test_isolation_guards.py    # 确认违规则必失败，包括错误被业务捕获
  test_dataset_integrity.py
  test_contracts.py
  test_dispatcher.py
  test_solver.py
  test_evaluators.py
  test_memory_isolation.py
  test_idempotency.py
  test_api.py
  test_durable_protocol.py
  run.py                      # 先设置进程环境，再导入 pytest/业务模块
```

计划入口：`python tests/offline/run.py`。入口负责设置明确测试路径、独立配置、临时输出目录、禁用自动加载非必要 pytest 插件及 .pyc 写入。不得导入或调用在线 run_eval 主流程。报告生成到临时根目录的 `reports/`，记录实际路径；不依赖当前 shell 的工作目录。

优先使用 pytest 参数化和标准 asyncio，不为运行而启动服务，不为每个用例新建复杂框架。必要的代码调整仅限依赖注入点：模型、存储、追踪器、时钟、HTTP 客户端与状态工厂，生产默认行为保持兼容。避免只为方便测试新增一套业务实现。

## 8. 分阶段交付与完成条件

1. 隔离基础：先验证网络/写入守卫，证明真实访问尝试即使被捕获也使测试失败；检查状态能复原。
2. 核心确定性：数据完整性、契约、门控、求解器与校验器，所有测试使用人工可核对预期。
3. 状态与调度：并行屏障、缓存失效、隔离、幂等、多轮修复与故障注入。
4. API 与任务协议：进程内组合测试；有条件再加入真实临时 durable runtime 的独立档。

完成必须满足：

- 新增测试实际可运行，命令退出码可靠，失败返回非零。
- 无真实模型调用、无网络连接、无正式存储访问、无临时根目录外业务写入；所有违规数为零。
- 1604 条源数据在测试前后哈希一致；业务代码读取的仅是规定输入。
- 每个关键机制都有正常、异常和边界断言；故意构造错误结果时测试能发现错误，而非只断言不抛异常。
- 报告分别列出通过、失败、跳过、不可运行及原因。核心测试因依赖缺失而跳过不能算验收完成；已知缺陷不得静默 xfail。
- 不输出伪造的“模型准确率”。记录代码测试数、数据校验数、独立场景组数和未覆盖边界，各自分开统计。

本方案不包含真实模型评测、官方 DSL 适配、RAG 扩容或生产数据库测试。若未来开展，另设显式入口、专用测试环境与独立报告。
