# 差旅助手自动化测试完善方案：面向测试岗实践

日期：2026-11-04。状态：设计稿，尚未实施新增内容。

本方案补充 `AUTOMATED_TEST_PLAN.md`，以本文件的分阶段范围和完成条件为准。现有 33 项离线测试继续保留；现有 `--full` 仅表示运行已实现的扩展档，不代表本方案全部完成。

## 1. 要证明什么

目标是形成一个可复现的测试实践：需求分析 → 风险识别 → 用例设计 → 自动执行 → 缺陷复现 → 根因定位 → 修复回归 → 报告与持续集成。

测试对象是代码及其组合行为，不验证模型智能水平。模型、搜索、天气、外部工具全部使用受控替身；真实调度、契约、求解器、校验器、记忆逻辑和接口应尽量保留。不能把整个被测业务函数替换成固定结果后，宣称完整链路通过。

本次不调用付费 API，不下载模型权重，不使用真实用户数据，不连接正式或现有本地数据库。依赖安装阶段可以下载软件包，测试执行阶段禁止外部访问。真实模型质量、本地模型部署、官方 ChinaTravel 评分、真实 PG/Redis 并发语义及生产压测均不在本次验收范围内。

## 2. 先明确需求和预期，再写断言

每条需求必须有稳定编号、业务规则、风险、测试方法和验证证据。无法确定的产品行为先列为待定义，不以现有实现直接充当正确答案。

以下为建议的目标规则，需要在测试设计阶段明确接受范围：

| 需求编号 | 应满足的规则 | 风险与关键观察点 |
| --- | --- | --- |
| REQ-API-01 | 输入合法时返回约定结构；非法输入在进入业务前拒绝 | 422/业务错误边界、空白输入、字段类型、无业务副作用 |
| REQ-GATE-01 | 缺必要行程要素先追问；补充后可续跑 | 不擅自补日期、不漏接上一轮城市、不调用被门控技能 |
| REQ-STATE-01 | 请求上下文从开始到完成均属于原用户和会话 | A/B 会话交错时响应、trace、记忆和缓存不串 |
| REQ-IDEM-01 | 去重有效期内，同用户同请求不重复执行；不同用户不互相命中 | 在途等待、完成回放、失败释放、TTL 边界 |
| REQ-IDEM-02 | 同 request_id 配不同内容时采用明确且一致的策略 | 当前是优先 request_id 回放；应记录这一语义，不能默认系统会拒绝冲突 |
| REQ-CACHE-01 | 只有输入依赖仍有效时才能复用旧结果 | 更换城市、日期、天数、偏好分别影响哪些技能 |
| REQ-MEM-01 | 偏好更新按追加/覆盖语义落库，缓存不返回旧状态 | 写失败、失效失败、读写交错、JSON 往返 |
| REQ-PLAN-01 | 代码对其明确建模的约束给出正确判定 | 活动预算口径、必去项、时间窗、无解与超时区分 |
| REQ-FAIL-01 | 部分失败、取消、超时均结束在明确状态 | 请求不永久占键、in-flight 不泄漏、其他任务不误丢 |
| REQ-HISTORY-01 | 历史、删除、回放行为一致且不影响其他会话 | 消息顺序、结构化行程、关联缓存、删除范围 |
| REQ-DURABLE-01 | 已接受的任务不因等待失败而在本地重新执行 | submit 与 wait 故障语义、同标识接续、可观察派发次数 |
| REQ-SEC-01 | 输入不能造成跨用户读取或路径逃逸 | 当前缺身份认证；ID 过滤与权限隔离必须分别报告 |

例如，“删除会话是否同时删除全局偏好和行程历史”不能凭猜测断言。建议只删除该会话记录与会话缓存，用户长期资料是否删除另设操作；实现前先固化规则。

## 3. 测试分层，避免只测替身

| 层次 | 运行真实部分 | 允许替换部分 | 结论边界 |
| --- | --- | --- | --- |
| 单元与规则 | 契约、校验、求解、键生成、状态机 | 时钟、随机源、外部依赖 | 局部规则正确性 |
| 模块组合 | 意图结果解析、dispatcher、runner、MemoryManager | 模型输出、网络工具、存储连接 | 多模块数据流与状态处理 |
| 接口组合 | FastAPI 路由、Pydantic、幂等、pipeline、聚合、真实 JSON 临时存储 | 模型工厂、外部查询、数据库连接、durable HTTP | 从请求到结果和持久化的产品代码路径 |
| 持久任务专项 | 当前真实 TS 任务定义、runtime、临时 SQLite | 模型 provider、Python 回调 | 实际被覆盖路径的恢复与副作用行为 |

接口组合使用 httpx ASGITransport 在进程内发请求，不监听端口；显式执行受控 lifespan，验证资源初始化和关闭。不要把 `_chat_execute` 整体 mock 掉。框架连接和配置应有可注入入口，生产默认行为兼容，禁止仅为测试另外复制一套业务代码。

现有 Windows 无 socket 事件循环仅支持当前协程测试，不能直接声称已覆盖 ASGI 生命周期、线程和真实 runtime。新层必须验证其运行条件；若不兼容，使用支持进程内 ASGI 的独立执行环境，不放开任意 localhost 访问来让测试变绿。

## 4. 关键用例设计

以下是首先实现的高风险场景，每组都有正例、反例或边界，不按“写满多少条”验收。

### CASE-01 接口参数与业务副作用

- 设计等价类：正常中文需求、空字符串、纯空白、缺 message、null、错误类型。
- 长度边界：message 为 1、20000、20001 字符；request_id 为 128、129 字符。
- user_id、session_id 检查空值、非法路径字符、跨用户相同名称；无明确限制的字段记录需求缺口。
- 断言状态码与响应字段、模型/技能调用次数、临时记忆与 trace 是否变化。纯空白是否应拒绝是目标业务规则，不能把未实现行为写成已满足。

### CASE-02 缺信息追问与补充续跑

固定输出依次模拟：第一轮只提取杭州；第二轮提取杭州、三天和固定日期。

- 第一轮断言 needs_input、缺失字段集合、规划调用为零。
- 第二轮通过同一会话请求，检查意图模块实际收到的近期对话、规划入参和最终落库内容。
- 再用新会话只发送“三天”，验证没有借用上一会话目的地。
- 不声称验证了模型能从“三天”理解杭州，只验证代码将历史传给了正确位置。

### CASE-03 同用户双会话交错

用 asyncio Event 控制顺序，不靠 sleep 碰运气：

1. A 会话请求杭州行程，在可控的技能执行点暂停。
2. 同用户 B 会话请求北京行程，推进到绑定上下文并完成。
3. 释放 A，让其完成。
4. 分别通过历史接口及存储观察结果。

必须检查 A/B 的响应 session_id、目的地、聊天记录、trace 的 user/session/turn、重规划缓存归属；错误不能只在页面文本里找。再做反向完成顺序和不同用户同 session_id 的组合。当前共享 pipeline 是风险来源，先写能稳定复现的失败测试，再讨论修复。

### CASE-04 请求去重

- 两个同用户同 request_id 请求：在途第二个等待，业务计数一次，结果一致。
- 完成后再请求：回放同一响应，持久化记录不增加。
- 第一遍执行异常：释放键后重试确实重新执行。
- 同 request_id 不同用户：分别执行，不互相回放。
- 固定时钟测试 TTL 前、到期、过期后的规则；还要检查执行中 TTL 到期是否允许重复业务执行。
- 以两个客户端模拟独立调用方，但只能证明当前内存守卫作用域；多实例分布式保证不得由此推导。

### CASE-05 重规划缓存失效决策表

| 修改 | 必须重新获取/计算 | 可考虑复用，但须核对输入依赖 |
| --- | --- | --- |
| 杭州改北京 | 城市信息、差标、比价、天气、行程与费用 | 与城市无关的用户偏好 |
| 仅改出发日期 | 日期相关天气、票价、冲突、行程 | 无版本变化的城市政策 |
| 三天改五天 | 费用、排程及受新日期区间影响的信息 | 不按天计费的政策原文 |
| 改酒店偏好 | 偏好与相关住宿/方案分析 | 目的地和日期未变的天气 |
| 上轮技能失败 | 失败技能及受影响的下游 | 其余成功且有效的结果 |

预期以业务依赖为依据，不机械复用整批 P1。替身记录调用入参和次数，用旧结果中的标记值观察是否流入新方案。若当前实现没有缓存依赖信息，应测试失败并登记缺陷，而非直接降低预期。

### CASE-06 偏好缓存读写交错

先测真实内存/JSON存储，再用带屏障的 FakeRedis 控制操作：

1. 数据库旧偏好为如家、缓存已命中。
2. 写万豪时暂停在失效和写库之间，插入并发读取。
3. 写入完成后再次查询，检查是否持久读到旧缓存。

追加/覆盖、去重、写库失败、缓存删除失败分别验证。FakeRedis 只能证明业务操作顺序，不能证明真实 Redis/PG 的事务性。

### CASE-07 规划与校验的闭环

- 用小型活动池跑真实 OR-Tools，以独立运算检查时间窗、时长、交通间隔、必去项和活动花费。
- 让模型替身输出故意改变求解排程的文案，验证后续是否能发现；不能只测求解器自身。
- 第一遍坏、第二遍好：检查缺陷反馈与调用次数；两遍均坏：检查警示和产品既定放行策略。
- 提取失败、无活动、缺求解器、求解未知/超时、评估器抛错分别验证状态，不能把未知统一当无解。
- 活动门票预算与全行程费用分开验收；不宣称验证了真实开放时间和价格。

### CASE-08 部分失败与取消

并发执行中分别注入一个技能抛错、固定超时、无效 JSON、取消请求。断言成功结果仍可使用、错误可定位、无无限重试，in-flight 恢复到请求前基线，幂等状态和后台任务按规定结束。指标差分基于本次隔离 registry，不读取正式全局监控数据。

### CASE-09 历史、删除与展示数据契约

完整走“发起→生成→落库→查询→删除→再查”，检查消息顺序、结构化 itinerary 和每轮标识一致。删除 A 不得删除 B；临时 SQLite/JSON 内的数据要与接口表现一致。

前端渲染测试后置：先验证后端聚合 JSON 与历史回放结构，再用离线 fixture 检查卡片绑定；不靠截一张页面图证明后端数据正确。

### CASE-10 durable 的两类证据

- Python 协议层：submit 失败、提交后 wait 失败、重复 task_id、已完成结果回放。断言已接受后不会在本地另起一次执行。
- TS runtime 层：使用当前 PipelineTask → SkillGenTask 路径，不只测试旧 SkillTask；记录 replay 声明是否真正参与恢复决策。
- 恢复专项：在临时 checkpoint 已提交后结束工作子进程，再用同一临时 SQLite 启动新进程，观察派发次数和结果。关闭/重开对象的测试只标为对象重建，不等同真实进程崩溃。
- 故障点包括派发前、派发后未回执、结果完成未 finalize、记忆写入后未缓存响应。每个故障点单独说明可能重复与可能丢失的窗口。
- 若模型 provider 无法使用固定输出运行真实 runtime，该路径标为未验证，不调用真实模型凑通过。

此档需要允许受控测试父进程管理工作子进程，但工作子进程仍禁止外部网络和任意进程启动。与默认禁止 subprocess 的审计档分开，限定启动命令、临时路径和超时，不全局关闭守卫。

## 5. 数据、替身和环境治理

### 数据分区

- 原始 ChinaTravel、原生 cases.json 只读并校验哈希。
- 挑选少量 Easy/Medium/Human 需求作为代码场景素材，人工复核后另存 fixtures，记录 source_uid、改编点、固定日期、模型输出和预期。
- Human1000 只做格式完整性校验，留给后续模型评测，不据其内容调试提示词。
- 每条测试独立 run_id/case_id；需要验证相同用户或请求时在该测试内部显式共享，测试之间不共享状态。

### 替身设计

ScriptedModel 按预期顺序返回固定文本/异常，记录消息和调用次数，额外调用立即失败。天气、搜索和 HTTP 替身对请求方法、路径和参数做精确匹配，未登记请求必须失败，不返回万能成功响应。

预期结果由需求和手工小样本独立定义，不能复用生产函数生成 expected。避免给替身完整“标准答案”后只断言该答案出现在响应中。

### 隔离

不读取真实 config、密钥、记忆、Milvus 或 session.sqlite。所有可写路径、缓存、报告、SQLite 进入本次临时根目录；运行结束检查违规账本和输入哈希。资源清理只作用于本次创建的目录和进程，不执行清表或 FLUSHDB。

Python audit hook 是误用防线，不是对原生库的完整网络沙箱。真实 native runtime 档若要声称严格阻断外联，应在无外网权限的隔离执行环境中运行；否则明确缩小结论，不把“无审计事件”当作所有系统调用均被拦截的证明。

## 6. 测试工程组织

保留现有 unittest 用例，不重写已经有效的断言。新组合测试建议使用 pytest 管理 fixture、参数化、mark 和 JUnit 报告；逐步引入，不为了换框架迁移全部代码。

建议新增：

```text
tests/
  design/
    requirements.md          # 需求和不明确项
    risk_matrix.csv          # 风险→用例→文件→结果
    cases.csv                # 前置/输入/步骤/预期/优先级
  integration/
    conftest.py              # 测试 app 工厂、隔离状态、生命周期
    test_chat_api.py
    test_session_interleaving.py
    test_replan_invalidation.py
    test_memory_consistency.py
    test_error_cleanup.py
    test_history_api.py
  fixtures/                 # 版本化静态输入，禁止真实用户内容
  defects/                  # 已复现缺陷及证据索引
  offline/                  # 保留现有 33 项及隔离入口
```

新增受控入口按 smoke / regression / recovery 分档运行。装配顺序为：设置测试环境 → 安装隔离守卫 → 注入测试依赖 → 导入业务 → 执行指定测试路径。普通 `pytest tests` 不作为安全入口，不得误发现在线评测脚本。

需要的少量生产代码改动应是可复用依赖注入点：app/state 工厂、模型工厂、记忆路径与存储、时钟、trace 和 HTTP 客户端。每次改动单独说明原因并先回归原有 33 项。

## 7. 缺陷记录与验证测试有效性

一份缺陷记录至少包含：编号、对应需求、环境与版本、测试数据、最短复现步骤、预期/实际、脱敏请求与响应、状态/存储证据、严重程度、原因、修复位置和回归结果。

源码阅读发现的风险先标“待复现”，不要直接写“已发现并修复”。产品规则有争议的先列需求问题，不为通过测试修改需求。

选择若干关键规则做人工变异验证：临时副本中去掉 user/session 过滤、跳过门控、允许重复执行或移除一条求解约束，确认对应测试会失败。变异在临时副本执行，不改工作区业务文件；仅验证针对性的断言有效性，不用整体变异分数替代正确性。断言仅检查非空/200/不抛错的测试不能代表关键机制已覆盖。

## 8. 报告与持续集成

每次报告包含：环境/依赖版本、可获得时的代码提交号（当前目录无 Git 时记录源码哈希）、测试范围、需求覆盖、通过/失败/跳过/未运行、隔离违规、数据哈希、缺陷索引和已知限制。

失败报告保留最小证据，避免记录真实凭据；生成 JUnit XML 和简洁 HTML/Markdown 即可，先不增加复杂报告平台。

CI 文件先在本地验证；依赖安装为独立联网阶段，执行测试时使用测试配置，禁止真实服务凭据和出站业务访问。Windows 依赖快照不能直接当 Linux 通用锁文件。默认不运行在线评测和真实存储测试。仓库托管与 CI 平台尚未建立时，只交付配置，不声称 CI 已上线运行。

不追求任意 100% 行覆盖率。覆盖率用于发现关键错误分支未执行，需求矩阵用于说明风险覆盖，两者并用。测试耗时只用于发现卡死或异常回归，不作为真实模型延迟、吞吐或并发容量指标。

## 9. 分阶段实施和退出条件

| 阶段 | 交付 | 完成依据 |
| --- | --- | --- |
| A：设计基线 | 需求表、风险表、接口清单、数据字典 | 每个高风险需求有独立预期和对应用例；不明确规则显式列出 |
| B：接口与装配 | 测试 app 工厂、进程内 API 测试、隔离 fixture | 真实业务路由执行、lifespan 可控、无真实外联和数据污染；原 33 项仍通过 |
| C：状态专项 | 会话交错、去重、缓存失效、失败清理 | 屏障控制复现顺序，断言响应和落库；发现的问题有复现证据，修复与未修复分别列出 |
| D：恢复专项 | TS 当前任务路径、临时 SQLite、故障点测试 | 真正新进程恢复或明确标注未验证；不把旧路径结果移用于新路径 |
| E：回归工程 | 统一报告、需求追踪、CI 配置、运行手册 | 失败退出非零、缺依赖不能算通过；CI 在实际运行后才标已验证 |

先完成 A→B→C，再做 D 和 E。无需先收集上千条新用例，也无需先做付费模型评测。

最终验收不以“全部绿色”掩盖缺陷：核心已确认规则存在失败时必须列为未满足，不静默 xfail；关键档未运行时不得声称方案完成。对固定场景重复或改变完成顺序仅用于排除新的不稳定性，不通过无限重跑挑一次成功结果。

## 10. 测试岗面试产物

保留可展示的需求风险矩阵、代表性用例、可运行自动化代码、真实缺陷记录、修复前失败/修复后通过的证据，以及报告和 CI 运行记录。

可以据实介绍：“以差旅助手为被测系统，针对接口、会话状态、缓存和任务恢复开展分层自动化测试，使用替身控制外部依赖和故障，验证隔离与回归。”缺陷数量、覆盖率、运行收益等只有实际测量后再填写。现有 33 项是起点，不包装成企业级质量保证。
